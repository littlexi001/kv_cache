# 位置级证据预算与 PCA 压缩索引（2026-07-15）

## 1. 研究问题

本轮研究检验一个更细粒度的假设：不同生成位置需要的历史证据量不同。常见词、局部可预测词可能只需很低的 KV 预算；数字、专名以及低置信度推理位置可能需要更高预算。因此，预算不应只按样本或任务分配，还应随生成位置动态变化。

需要注意，“下一个词是不是 `and` 或 `nine`”在当前 forward 前并不可知。可部署控制器只能使用当前输入 token、过去隐藏状态、过去 logits，或者先执行一次低预算 provisional forward 后再决定是否重算，不能使用真实目标 token。

## 2. 已验证的关键现象

### 2.1 词法类型不是充分的关键性指标

在 sports/medicine、32K 上，0.5% 扫描相对 QAbs rerank 的 PPL 比值为：

| 位置类型 | PPL 比值 |
|---|---:|
| 含大写词 | 1.213 |
| 数字 | 1.083 |
| 功能词 | 1.102 |

数字并不总是最危险，功能词也不总是安全。因此不能只用词频或 token 类型分配预算。

### 2.2 模型置信度能反映证据不足

最终 top-1 probability 大于等于 0.6 的位置，0.5% 扫描 PPL 比值约为 1.013；小于 0.1 的位置约为 1.302。置信度比词法规则更接近真正的“证据需求”。

### 2.3 因果 lookahead router 有信号，但单次预测还不够强

严格使用 window 0 训练、window 1 校准、window 2 测试。四步历史控制器在 conformal level 0.60 下达到：

| 指标 | 结果 |
|---|---:|
| PPL / QAbs rerank | 1.0499 |
| 0.5% 动作 | 16.07% |
| 1% 动作 | 40.08% |
| 2% 动作 | 23.61% |
| rerank 动作 | 20.24% |

把 rerank 强制替换为 2% 后，PPL / QAbs rerank 为 1.0488，说明高成本 rerank 并非质量所必需；主要瓶颈转为低预算扫描的候选召回和运行速度。

## 3. 方法升级：Progressive Evidence Controller

对位置 `t`，先用最低预算 `b_0=0.5%` 计算 provisional 输出：

```text
(h_t^0, p_t^0) = Forward(x_t, KV_<t, b_0)
```

控制器使用 provisional entropy、top-1 probability、top-1/top-2 margin、检索 gap、候选稳定性和历史状态，预测最小安全预算：

```text
b_t = Router(phi_t),  b_t in {0.5%, 1%, 2%}
```

若 `b_t>b_0`，从同一份旧 cache 重算当前位置，并只提交最终一次产生的新 KV：

```text
(h_t, p_t) = Forward(x_t, KV_<t, b_t)
```

这个两阶段结构比纯 lookahead router 多一次低成本 provisional forward，但能看到当前输出位置的真实模型状态，并且不使用真实下一个 token。按 128K 子系统微基准估算，若 20% 位置从 0.5% 升到 2%，attention 时间约为 `0.423 + 0.2*0.919 = 0.607 ms`，相对 2.628 ms full attention 仍约为 4.33x。

## 4. PCA 压缩检索索引

原 QAbs 只扫描 query 绝对值最大的维度，但真实 Q/K trace 显示，单维重要性不是稳定子空间。对每层、每个 KV head，用前缀采样 key 的二阶矩估计 PCA 基：

```text
C_lh = (1 / |S|) * sum(K_lh,i^T K_lh,i)
U_lh = TopEigenvectors(C_lh, d)
```

随后存储低维量化索引：

```text
K_hat_lh,i = Quantize(K_lh,i U_lh)
q_hat_lh,t = Quantize(q_lh,t U_lh)
s_lh,t,i = q_hat_lh,t K_hat_lh,i^T
```

索引只负责找候选 token；最终 attention 仍使用候选位置的精确 K/V。

真实 Q/K trace 上的结果：

| 索引 | 索引/完整 KV | 2% retained mass | candidate recall@top2 |
|---|---:|---:|---:|
| QAbs16 FP16 | 50.00% | 0.8437 | 0.8775 |
| PCA32 INT8 | 6.64% | 0.8522 | 0.8908 |
| PCA48 INT8 | 9.77% | 0.8652 | 0.9587 |
| PCA64 INT4 | 6.64% | 0.8661 | 0.9588 |
| PCA96 INT4 | 9.77% | 0.8708 | 0.9807 |

这说明主要收益来自学习到的子空间，而不是单纯增加量化位宽。

## 5. 当前质量结果

PCA64 INT4、32K、window 0 的固定预算结果：

| 主题 | 0.5% PPL | 1% PPL | 2% PPL | QAbs rerank PPL |
|---|---:|---:|---:|---:|
| sports | 10.0150 | 9.7080 | 9.4442 | 9.1068 |
| medicine | 11.3002 | 10.8565 | 10.5283 | 10.1820 |

2% 平均 PPL 相对 QAbs rerank 约为 1.0355。`6.64% + 2% = 8.64%` 只是在每个 query head 独立选择 token 时的 attention-link 等价下界，不是 GQA 下可实现的 KV 存储比例。同一 KV head 对应的多个 query heads 可能选择不同 token，真实精确 K/V 占用必须统计这些候选的并集。该结果目前只覆盖 window 0，不能作为最终独立测试结论。

## 7. 真实 Progressive Controller 结果

router 只使用 0.5% provisional forward 的 entropy、top-k probability、margin 和位置特征。训练协议为 sports/medicine window0 训练、window1 校准、window2 首次测试。离线逐 token policy 在 window2 得到：

| PPL/full | 动作 0.5% / 1% / 2% | 索引 + per-query link 下界 | 128K attention 估计加速 |
|---:|---:|---:|---:|
| 1.0443 | 57.2% / 13.1% / 29.7% | 7.65% | 3.18x |

真实顺序运行后，window2 合并 PPL/full 为 1.0518，索引加 per-query link 下界约 7.63%，attention 估计 3.22x。轨迹误差使质量比离线 policy 差约 0.7 个百分点，因此后续结果全部使用真实顺序运行。

冻结策略只依据 calibration frontier 选择为 `conformal=0.5, safe_delta=0.08`。由于 sports 语料不足以构造不重叠的 window3，最终新 holdout 使用 medicine-window3 和训练从未见过的 computer-window0：

| Holdout | PPL/full | 0.5% / 1% / 2% | 索引 + per-query link 下界 | 128K attention 估计加速 |
|---|---:|---:|---:|---:|
| medicine-window3 | 1.0568 | 41.0% / 12.1% / 46.9% | 7.90% | 2.67x |
| computer-window0 | 1.0254 | 34.0% / 9.8% / 56.2% | 8.03% | 2.49x |
| 合并 | **1.0410** | 37.5% / 10.9% / 51.6% | **7.97%** | **2.58x** |

合并 PPL 为 15.096，full PPL 为 14.502。该结果不使用 oracle，不按真实目标 token 选动作，并且来自动态 cache 的真实顺序执行。

位置类型分析也支持“证据需求”而非硬编码词类：功能词中 66.7% 使用 0.5%，历史只出现不超过一次的稀有 token 有 35.5% 使用 2%，历史高频 token 只有 22.1% 使用 2%。数字 token 样本较少且常可由局部模式预测，并不总需要高预算。

### 7.1 加入检索稳定性并蒸馏轻量 router

初版 router 使用三个 600-tree ExtraTrees，单位置 CPU 推理约 75 ms，不能作为最终系统。新版本增加三个不需要额外 Transformer forward 的检索特征：候选 top1/top2 gap、top1/boundary gap、连续位置 top-32 候选交集；随后把 teacher 动作蒸馏为 `10 -> 16 -> 3` 的单隐层 MLP。

检索特征的 PyTorch 广播版本需要约 0.20 ms/层。融合 warp-level CUDA kernel 后为 0.0184 ms/层，数值最大误差 `1.19e-7`。MLP 单位置推理约 3.6 微秒。融合 kernel 复跑的动作和 PPL 与旧实现逐项相同。

最终冻结 MLP 在训练与校准均未出现的 space、politics 主题上真实顺序运行：

| Holdout | PPL/full | 0.5% / 1% / 2% | per-query 下界 | PCA 索引 + GQA KV 并集 | 含全部控制开销的 128K attention 加速 |
|---|---:|---:|---:|---:|---:|
| space-window0 | 1.0262 | 30.9% / 27.0% / 42.2% | 7.91% | 9.2625% | 2.51x |
| politics-window0 | 1.0482 | 32.8% / 23.4% / 43.8% | 7.91% | 9.2686% | 2.53x |
| 合并 | **1.0371** | 31.8% / 25.2% / 43.0% | **7.91%** | **9.2655%** | **2.52x** |

候选并集由 CUDA bitset kernel 直接逐层、逐位置统计，并与 CPU 参考逐项一致。外部 holdout 中，0.5%、1%、2% 三档 per-query 动作分别对应 1.107%、2.142%、4.032% 的 KV-head 并集；四个 query heads 的候选只放大约 2.0--2.2 倍，而不是最坏的 4 倍。最终动态精确 KV 并集为 2.625%，加 PCA32 INT8 索引 6.641%，得到 9.266% 的可实现逻辑存储。合并质量保持率为 `1 / 1.0371 = 96.42%`。

这是目前最强且最干净的结果：无 oracle、无真实目标 token、无测试主题训练，使用真实动态 cache 轨迹，并在速度核算中加入 query 投影、INT8 扫描、top-k、最终稀疏 attention、检索稳定性和 MLP router。

32K HuggingFace harness 中，full 平均在线时间为 33.66 秒，本方法融合复跑为 35.82 秒，即约 0.94x。当前规模下 MLP 和非 attention 开销占主导，尚不能把 2.52x 写成端到端生成加速。

### 7.2 GQA 组内共享候选：比动态 router 更强的固定方法

同一 KV head 服务 4 个 query heads。独立检索会产生 2.0--2.2 倍的候选并集，而 query heads 对相关历史位置通常存在共识。新路径先对 4 个 query heads 的 PCA 检索分数取均值，再以 KV head 为单位执行一次 top-k；4 个 query heads 共享同一组精确 K/V：

```text
s_bar_lh,i = (1 / G) * sum_g s_lh,g,i
I_lh = TopK_i(s_bar_lh,i, b)
Attention_lh,g = Attention(q_lh,g, K_lh[I_lh], V_lh[I_lh])
```

在 sports/medicine window0 上，`shared_mean` 在 0.5%、1%、2% 三档的合并 PPL 均比 query-head 独立检索低 1.2%--1.6%。这说明组内均值不仅减少物理候选，还会过滤单个 query head 的检索噪声。

冻结 PCA32 + shared-mean + 固定 2% 后，在三个不重叠窗口得到：

| 窗口 | PPL | Full PPL | PPL/full | 质量保持 |
|---|---:|---:|---:|---:|
| window0 | 9.8607 | 9.4770 | 1.0405 | 96.11% |
| window1 | 4.4918 | 4.4573 | 1.0077 | 99.23% |
| window2 | 14.6822 | 14.0006 | 1.0487 | 95.36% |
| 三窗口合并 | - | - | **1.0321** | **96.89%** |

该方法不需要 router，不需要 provisional forward，也没有动态复跑。PCA32 INT8 索引占完整 FP16 K/V 的 6.64%，共享精确 K/V 严格占 2%，所以逻辑存储为 8.64%。128K、RTX 3090 微基准中，完整在线 attention 路径为 0.770 ms，相对 full attention 2.628 ms 为 **3.41x**；其中已包含 query 投影与量化、INT8 Tensor Core 扫描、组内均值、8 路 top-k、索引广播和最终 ragged attention。

进一步缩小索引后，PCA16 + shared-mean 的结果为：

| 精确 KV 预算 | sports/medicine 合并 PPL | 索引 + 精确 KV | 128K attention 加速 |
|---:|---:|---:|---:|
| 2% | 10.3928 | 5.52% | 3.43x |
| 3% | 9.9533 | 6.52% | 2.35x |
| 4% | 9.8507 | 7.52% | 1.75x |

PCA16 + 4% 的质量略优于 PCA32 + 2%，但速度不满足 2.5x 目标。当前 Pareto 最优实用点因此是 **PCA32 + shared-mean + 固定 2%**。

在方法和预算冻结后，使用训练、校准和方法选择均未出现的 religion-window0 做外部测试：full PPL 为 12.2758，本方法为 12.3412，PPL/full 为 **1.0053**，质量保持 **99.47%**。该结果不使用 router，也未按 religion 调整 PCA 维数、预算或聚合规则。

### 7.3 从逻辑 8.64% 到分层物理存储

2% shared-mean 候选在 token 粒度下严格只需要 2% 精确 K/V，但直接采用固定页面会产生明显放大。sports/medicine-window0 的候选页面占完整 K/V 的比例如下；表中尚未加入 6.65% 的 PCA32 索引：

| 主题 | token 粒度 | page=16 | page=64 |
|---|---:|---:|---:|
| sports | 2.00% | 13.78% | 30.39% |
| medicine | 2.00% | 12.69% | 26.54% |

因此，16/64-token 固定分页不能满足 10% 常驻显存目标。另一方面，候选集合在相邻生成位置具有很强的时间局部性：前一位置候选可覆盖当前候选约 67%--69%，前两个位置的并集可覆盖约 75%--77%，前四个位置约 81%--83%。这支持采用 token 粒度热缓存，而不是扩大固定页面。

当前物理路径为：

```text
GPU: PCA32 INT8 index + 3.2% exact-KV hot cache + hash/LRU directory
CPU: full exact K/V in pinned mapped memory

shared top-2% candidates
  -> hash lookup resident slots
  -> LRU-histogram selects miss destinations
  -> mapped host writes only misses into evicted GPU slots
  -> sparse attention reads all candidates by GPU cache-slot index
```

五个主题的真实 32K/256-token 顺序轨迹中，3.2% 精确 K/V 缓存命中率为：

| 主题 | LRU 命中率 | 每步主存 miss / full KV |
|---|---:|---:|
| sports | 78.68% | 0.4264% |
| medicine | 80.91% | 0.3819% |
| space | 81.83% | 0.3634% |
| politics | 83.34% | 0.3332% |
| religion | 81.79% | 0.3643% |

sports 是当前覆盖内的最差情况：每步只需从主存读取完整 K/V 的 `2% * (1 - 78.68%) = 0.4264%`，在 128K、8 KV heads、FP16 K/V 下为 2.184 MiB/layer。后续 128K 物理路径测速采用该 worst-case miss 比例。

常驻物理 GPU 存储按字节统计为：

| 常驻状态 | 相对完整 FP16 K/V |
|---|---:|
| PCA32 INT8 codes + FP16 scales + PCA basis | 6.6528% |
| 精确 K/V 热缓存 | 3.1998% |
| hash keys/slots + inverse token ids + uint8 recency | 0.1045% |
| 合计 | **9.9571%** |

目录使用 8192-entry/head、load factor 0.512 的开放寻址表。融合 CUDA 管理器把 lookup、8-bit recency histogram 淘汰、槽位更新和 hash rebuild 的总时间从 PyTorch `searchsorted/topk/sort` 的约 0.299 ms/layer 降到 **0.0502 ms/layer**。uint8 recency 每步衰减并把命中项置为 255；超过 255 步未访问的冷项允许并列，当前 256-token 轨迹内与精确 LRU 的有效时间范围一致。修复 age 衰减与 hit 刷新之间的 block 同步竞态后重新编译，耗时仅比修复前增加 0.0004 ms/layer。

128K、RTX 3090 的保守组件核算为：

| 在线组件 | 时间 / layer |
|---|---:|
| query PCA 投影/量化 + INT8 scan + shared top-k | 0.2119 ms |
| hash lookup + recency/LRU update + hash rebuild | 0.0502 ms |
| mapped-host miss 直写 cache + cache-slot sparse attention | 0.7410 ms |
| 合计 | **1.0031 ms** |

相对同一微基准中的 full attention 2.628 ms/layer，component-composed attention 数据路径为 **2.62x**。mapped-host 写入、cache-slot attention 和 GQA 参考的数值最大误差均为 0。该数字包含 query 处理、检索、目录管理、PCIe mapped read、cache writeback 和最终 attention，但仍不是 HuggingFace 端到端生成速度；后文单独报告真实模型的 decode 与完整流程时间。

两个负结果也已明确：固定 page=16/64 的页面放大无法满足显存目标；让每个 query head 直接读取 mapped host 会重复读取 GQA 共享 K/V，且 block 数不足，实测显著慢于“miss 先写热缓存、再按 slot attention”。

### 7.4 真实 HuggingFace cache 生命周期验证

已经实现 `HierarchicalPCACache` 并接入 Llama 逐 token decode。prefill 后，原始 GPU full K/V tensor 被清空；完整精确 K/V 转入 pinned CPU memory，GPU 只保留 PCA32 INT8 索引、3.2% 精确热缓存、目录和当前 token 槽位。该路径不是只修改 attention mask 的逻辑模拟，而是实际按分层状态执行检索、miss 搬运和 cache-slot attention。

固定 PCA32、shared top-2% 和 3.2% 热缓存，在三个 32K 主题上均使用 `31744 remote + 256 query warm-up + 256 target` 协议：

| 主题 | full PPL | 旧算法参考 PPL | 真实物理 PPL | 物理 / full | 物理 / 旧算法 | 热缓存命中率 |
|---|---:|---:|---:|---:|---:|---:|
| sports | 8.7902 | 9.0581 | 9.0703 | 1.0319 | 1.00135 | 78.75% |
| medicine | 10.2239 | 10.7344 | 10.7366 | 1.0501 | 1.00020 | 80.94% |
| religion | 12.2758 | 12.3412 | 12.3426 | 1.0054 | 1.00011 | 81.85% |
| 三主题合并 | - | - | - | **1.0290** | **1.00055** | - |

三主题合并质量保持为 **97.18%**。物理实现相对旧算法参考的最大 PPL 漂移只有 0.135%，说明 CPU/GPU 分层和热缓存 miss 路径没有引入实质算法回归。

32K fused 实际 tensor 字节统计为：GPU 常驻层次化 KV 状态 421,716,736 bytes，pinned CPU 精确 K/V 4,228,907,008 bytes。相对最终长度 32,255 token 的等价 full GPU KV，常驻比例为 **9.9750%**；相对预分配容量 32,264 token 为 9.9722%。若只用转换瞬间的 31,744 remote token 作分母，比例为 10.1356%，这是因为分子已预留后续 520 个 token 的索引和当前 token 槽位，不能作为稳态压缩率。fused hash table 比 sorted correctness 目录多占约 3.16 MB，但稳态仍低于 10%。

真实生命周期已经替换为支持每个 KV head 不同 hit/miss 数量的 fused hash-LRU，并使用 miss mask 直接从 mapped host 填入目标 cache slot，不再由 CPU 整理变长 miss 集合。为避免异步 CUDA 队列错记时间，full 与本方法都在每个 token forward 前后同步；在同一张 RTX 3090 上顺序执行，结果为：

| 32K religion 同协议 | Full SDPA | Fused 分层缓存 | 加速 |
|---|---:|---:|---:|
| prefill | 16.701 s | 18.177 s | 0.919x |
| cache 转换 | 0 | 6.683 s | - |
| 511 步 decode | 50.711 s | 33.114 s | **1.531x** |
| prefill + 转换 + decode | 67.412 s | 57.975 s | **1.163x** |
| 每步 decode | 99.24 ms | 64.80 ms | **1.531x** |

额外 setup 成本在约 237 个 decode step 后摊平。最终进程 allocated GPU memory 从 20,297,539,584 bytes 降至 16,493,408,768 bytes，下降 18.74%；由于模型权重不变，该进程级比例远小于 KV 自身 90.03% 的节省。两条路径的 prefill/转换峰值 allocated 都是 21,462,139,392 bytes，因为转换时必须短暂同时持有 full prefill KV 和已建立的部分分层状态；这是下一阶段需要通过流式 prefill 建索引消除的问题。

### 7.5 真实长度缩放：速度兑现，但 128K 出现质量拐点

32K、64K、128K 都采用相同的 religion 流、`256 query warm-up + 256 target` 和逐 token 全设备同步计时。64K 使用两张 RTX 3090，128K 使用四张 RTX 3090；每个长度内的 full 与本方法使用相同 `balanced` 映射，因此同一行的加速可比较，但不能把不同行的绝对秒数直接视为单卡长度缩放。

| 长度 | Full PPL | 本方法 PPL | PPL / full | 常驻 KV | 热缓存命中 | decode 加速 | 含 prefill/转换总加速 | 进程最终 allocated 降幅 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 32K | 12.2758 | 12.3426 | 1.0054 | 9.9750% | 81.85% | **1.531x** | **1.163x** | 18.74% |
| 64K | 7.1099 | 7.0285 | 0.9885 | 9.9735% | 84.11% | **2.366x** | **1.361x** | 30.92% |
| 128K | 15.9575 | 20.4390 | **1.2808** | 9.9727% | 83.17% | **2.340x** | **1.231x** | 45.98% |

64K 的 511 步 full/physical decode 分别为 89.123/37.660 秒；128K 分别为 167.393/71.548 秒。128K 的真实 decode 加速已经接近组件路径的 2.62x，说明此前“小长度下 attention 占比不足”的判断成立。128K cache 转换为 23.241 秒，约 128 个 decode step 后摊平。常驻 KV 仍严格低于 10%，最终进程 allocated 从 32.907 GB 降至 17.777 GB。

但是，128K 的质量保持只有 `15.9575 / 20.4390 = 78.07%`，未达到 95% 门槛；该长度点只能证明系统可扩展性，不能作为主方法质量结果。误差也不是由极少数异常 token 独占：256 个位置中 70.31% 的 NLL 变差，NLL 差中位数为 0.136。

### 7.6 128K 失败诊断与两阶段精确证据重排

固定使用 128K 样本的前 32 个目标 token，full PPL 为 15.1605。受控消融为：

| 检索配置 | PPL | PPL / full | 结论 |
|---|---:|---:|---|
| PCA32，粗候选 2%，最终 attention 2% | 24.1930 | 1.5958 | 原始失败点 |
| PCA32，粗候选 3%，最终 attention 3% | 25.9052 | 1.7087 | 单纯扩大候选反而变差 |
| PCA64，粗候选 2%，最终 attention 2% | 27.1153 | 1.7886 | 单纯扩大投影维度没有修复 |

这排除了“索引更宽或候选更多就自然恢复”的假设。更符合结果的解释是：PCA 近似分数中的假阳性被直接送进最终 softmax，增加候选会把更多干扰项一起纳入 attention。两组诊断首次重新编译 CUDA 扩展，编译发生在第一次 forward 内，因此其 `online_seconds` 不可用于速度比较；PPL 不受编译影响。

两阶段 shared 动作保持 PCA32 索引与 3.2% 精确热缓存不变：

```text
PCA32 shared score 召回 3% token
  -> hash/LRU 将精确 K/V 填入 3.2% 热缓存
  -> 用四个 GQA query heads 的精确 QK 共享分数重排
  -> 只保留精确 top-2% 做最终 attention
```

该结构把“检索召回预算”和“最终证据预算”解耦。常驻 GPU KV 仍约 9.97%，最终 attention 仍为 2%；新增成本是对 3% 热缓存候选执行一次精确 QK 重排。但是 128K 前 32 token 的 PPL 为 25.5069，PPL/full 为 1.6825，只比直接 3% attention 的 25.9052 略好，且比原始 shared 2% 的 24.1930 更差。因此近似候选假阳性不是主要瓶颈，shared 两阶段不能作为主方法。

### 7.7 Exact 预算上界：1% per-head 是 128K 最小安全档

使用完整 QK 计算每个 query head 的真实 top-k，再只对选中 V 做精确 attention。该实验是不可部署的 oracle，仅用于判断预算本身是否足够。相同 128K religion 前 32 token 的结果为：

| Exact per-head 预算 | PPL | PPL / full | 质量保持 | 判定 |
|---:|---:|---:|---:|---|
| 0.5% | 16.6221 | 1.0964 | 91.21% | 不安全 |
| 1% | 15.8072 | 1.0427 | **95.91%** | 最小已验证安全档 |
| 2% | 15.3101 | 1.0099 | **99.02%** | 接近 full |

full PPL 为 15.1605。该结果证明 128K 的质量失败不是稀疏 attention 的理论上界，而是 PCA 候选和 GQA 共享物理集合没有覆盖每个 query head 的专属证据。4K 同一主题窗口上，exact per-head 1% PPL 为 31.6637，而 full 为 25.2822，说明安全预算还随上下文长度、位置和局部文本变化；不能把 1% 硬编码成全局常数。这与“关键位置使用高预算、容易位置使用低预算”的位置级控制目标一致。

### 7.8 Per-head 虚拟候选：修复 128K 质量的正结果

新实现仍只保存 KV-head 级物理 K/V，但检索和最终 ragged attention 允许同一 KV head 下的四个 query heads 使用不同 token 集合。第一版为便于隔离机制，按最坏情况保存四段候选，尚未跨 head 去重：

```text
PCA index 一次扫描
  -> 每个 query head 独立 top-k 虚拟候选
  -> KV-head 目录装入四个候选集合的物理并集/最坏四段
  -> 每个 query head 只按自己的 slot 列表做 ragged attention
```

128K 前 32 token 的结果：

| 配置 | PPL | PPL/full | 质量保持 | 最终 attention | 常驻 KV |
|---|---:|---:|---:|---:|---:|
| PCA32 INT8，per-head 直接 1% | 21.5557 | 1.4218 | 70.33% | 1%/head | 10.985% |
| PCA32 INT8，per-head 召回 2% 后精确重排 1% | 15.9499 | 1.0521 | **95.05%** | 1%/head | 15.317% |
| PCA64 INT8，per-head 直接 1% | 15.8283 | 1.0440 | **95.78%** | 1%/head | 17.249% |
| PCA64 INT4，per-head 直接 1% | 15.7358 | 1.0379 | **96.34%** | 1%/head | 10.999%（四组同时驻留） |
| exact-QK oracle，per-head 1% | 15.8072 | 1.0427 | 95.91% | 1%/head | 不可部署 |

PCA64 INT8 per-head 1% 已几乎追平 exact-1% oracle，说明增加稳定子空间维度比 PCA32 的 2 倍 oversampling 更有效；per-head 虚拟候选是当前真正修复 128K 的机制。PCA64 INT4 不但没有带来质量下降，PPL 还从 15.8283 小幅降到 15.7358；该差异可能来自量化扰动对近似排序的正则化作用，不能在单一样本上解释为稳定提升，但足以确认 INT4 索引可用。

降低 INT4 投影维度不能替代 PCA64：PCA48/PCA56 INT4 的 PPL 分别为 16.4435/16.1373，质量保持只有 92.20%/93.95%；虽然常驻 KV 分别降到 9.429%/10.214%，但未达到 95% 门槛。因此后续固定使用 PCA64 INT4，把优化重点放在物理候选驻留方式，而不是继续削减索引维度。

### 7.9 Residency-windowed GQA：在 10% 内保留逐头证据

四个 GQA query heads 的候选并集可能超过 3.2%，但任意单个 query head 只需要 1%。新路径不再要求四个 head 的候选同时驻留，而是把同一 KV head 的 query heads 分窗口执行：

```text
PCA64 INT4 一次扫描，得到每个 query head 的独立 top-1%
  -> 每次取两个 GQA query heads，将两个 1% 列表直接拼为至多 2%
  -> 一次 fused hash/LRU + mapped-host miss fill
  -> 同时计算这两个 query heads 的 ragged attention
  -> 复用同一个 3.2% 物理热缓存处理下一对 heads
```

这里的关键是区分“逻辑证据集合”和“同时驻留集合”。四个 head 的逻辑候选仍全部保留，没有做 shared top-k，也没有因缓存容量而截断；只改变计算顺序，使物理缓存按两个 head 的窗口复用。直接拼接允许少量重复 token 占两个目录位置，但避免了显式 bitset 去重、compact 和二次 hash lookup。4K 数值 smoke test 中，单-head 流式、双-head 显式并集和双-head 直接拼接的 PPL 均为 34.377241，证明调度不改变 attention 结果；在线时间分别为 8.796、8.756、7.363 秒。

相同 128K religion 前 32 token、四张 RTX 3090、逐 token 全设备同步的正式结果为：

| 路径 | PPL | 质量保持 | 常驻 KV | 热缓存命中 | 287 步 decode | 相对 full 加速 |
|---|---:|---:|---:|---:|---:|---:|
| Full SDPA | 15.1605 | 100% | 100% | - | 94.054 s | 1.000x |
| 四组同时驻留，4.1% 热缓存 | 15.7358 | 96.34% | 10.999% | 82.30% | 31.279 s | 3.007x |
| 单-head 流式，3.2% 热缓存 | 15.7358 | 96.34% | 9.9918% | 83.14% | 40.768 s | 2.307x |
| 双-head 显式并集，3.2% 热缓存 | 15.7358 | 96.34% | 9.9918% | 80.89% | 37.314 s | 2.520x |
| **双-head 直接拼接，3.2% 热缓存** | **15.7358** | **96.34%** | **9.9918%** | **81.52%** | **35.018 s** | **2.686x** |
| 单-head 流式，1.1% 热缓存 | 15.7358 | 96.34% | 7.8265% | 47.65% | 44.519 s | 2.113x |

当前主结果为双-head 直接拼接：它第一次在真实 HuggingFace cache 生命周期中同时满足 `<10%` 常驻 KV、`>95%` 质量保持和 `>2.5x` decode。其 prefill、cache 转换和 decode 分别为 214.659、24.927、35.018 秒；full 的 prefill 和 decode 为 219.954、94.054 秒，因此包含全部阶段的协议总加速为 **1.143x**。1.1% 热缓存版本构成更激进的显存端点，但由于命中率下降，速度不是 Pareto 最优。

短上下文不能直接硬编码 1%：4K 上 PCA64 INT4 per-head 1%/2%/3%/4% 的 PPL 分别为 34.3772/31.8303/29.1423/28.1774，而 full 为 25.2822；即使 4% 也只有 89.72% 质量保持。当前正确策略是在短上下文保留 full fallback，在真正长上下文启用流式逐头检索；后续位置级 router 需要同时使用长度与当前 token 风险，而不能只预测 token 类型。

### 7.10 独立 computer 主题：固定 1% 失败，但 1.5% 是同存储安全动作

在上述方法与参数完全冻结后，使用此前五主题 cache-trace 统计未覆盖的 `computer/comp.graphics` 主题进行 128K 前 32 token 复验。固定 1% 没有通过质量门槛，因此 religion 的正结果不能直接外推为通用结论：

| 动作 | PPL | Full PPL | 质量保持 | 常驻 KV | decode 加速 |
|---|---:|---:|---:|---:|---:|
| per-head 1%，双-head 流式 | 65.7822 | 60.4325 | **91.87%** | 9.9918% | **2.761x** |
| per-head 1.5%，双-head 流式 | 60.5298 | 60.4325 | **99.84%** | 9.9918% | **2.278x** |
| per-head 2%，单-head 流式 | 57.1567 | 60.4325 | 105.73% | 9.9918% | 1.528x |

三档都复用同一个 3.2% 物理热缓存，所以逻辑预算增加没有增加常驻显存；1.5% 的两个 query-head 列表最坏同时占 3%，仍可双-head 执行，2% 则必须退回单-head 流式。computer 上 1.5% 是最小已验证安全动作，证明动作集合具有实际可恢复性，但固定使用会低于 2.5x 速度目标。

1% 相对 full 的 32 个位置中有 23 个 NLL 变差，中位差为 0.083；最差四个位置贡献 48.7% 的正向 NLL 损失。把固定 1% 和固定 1.5% 两条独立轨迹的 token NLL 做 teacher 级拼接，只升级收益最大的 2/32 个位置即可达到 95.22% 质量保持，按固定动作实测成本线性估计为约 2.72x decode。该结果只证明位置级稀疏升级的潜力，不能作为最终 router 指标：它使用目标 NLL 排序，而且不同固定动作轨迹的 hidden state 并不等同于真实混合轨迹。下一步必须训练只看因果特征的 router，并在新窗口上运行真实混合 cache 轨迹。

## 8. 已排除方向

- 全维 INT2 索引：候选召回约 71%，真实 PPL 明显恶化。
- groupwise INT2：存储从约 6.65% 增至 7.82%，召回反而下降。
- 仅用词法类别或长尾词判断关键位置：泛化信号不足。
- 在第 16 层之后才提升预算：只能小幅修复，说明错误候选会在早层累积。
- 固定 16/64-token 页面：候选页面放大到约 12.7%--30.4% 的精确 K/V，无法与 PCA32 索引共同压到 10%。
- query-head 独立 mapped-host attention：重复读取 GQA 共享 K/V，速度明显差于 KV-head 级 miss 写回。
- shared 候选从 2% 扩到 3%：增加干扰项，128K PPL 从 24.1930 恶化到 25.9052。
- shared 3% 粗召回后精确重排到 2%：128K PPL 25.5069，未修复 GQA head 专属证据缺失。
- 只在 shared 最终重排阶段做 head-balanced 配额：4K PPL 29.2822，差于在粗召回阶段保护 head 覆盖的 27.8332。

## 9. 尚未兑现的部分

1. 真实 HuggingFace fused cache 已在 32K/64K/128K 完成同协议测量；decode 加速分别为 1.531x、2.366x、2.340x，不能再把 2.62x 组件数据写成端到端速度。
2. 固定 PCA32 shared top-2% 在 128K 的质量保持只有 78.07%；PCA64 INT4 per-head + residency-windowed GQA 已在 9.9918% 常驻 KV 下恢复到 96.34%，并取得 2.686x 同协议 decode 加速。
3. 当前正结果仍只覆盖一个 128K 主题窗口的前 32 个 target token；在完成独立主题、更多窗口和任务型生成前，不能把该数字写成普适质量结论。
4. 0.5%/1%/2% 的位置级动态预算仍需蒸馏为不看真实目标 token、也不计算 full QK 的在线控制器；exact 预算前沿只提供 teacher/上界。
5. cache 转换已纳入完整核算，但当前转换仍先建立 full GPU KV，再逐层构建 PCA 并转入 CPU，所以峰值显存没有下降。需要在 chunked prefill 中在线构建索引和直接落 host KV。
6. 3.2% LRU 命中率已覆盖 sports、medicine、space、politics、religion；真实 fused PPL 已覆盖 sports、medicine、religion，仍需在 LongBench、RULER 和 Long ICL 的任务型生成轨迹上复核。
7. 仍需要更多模型、上下文长度和 batch size 的外部质量、显存和吞吐验证。

## 10. 下一步判定门槛

- 冻结 PCA64 INT4 + per-head top-1% + 双-head直接流式驻留，在未参与方法选择的 128K 主题/窗口上复现 `<10% KV、>95% 质量、>2.5x decode`。
- 短上下文暂时使用 full fallback；在独立长上下文窗口上蒸馏 0.5%/1%/2% exact 安全标签，训练只使用 provisional logits、检索 gap/稳定性、上下文长度和历史状态的位置级控制器。
- 将 PCA/index 构建和 host-KV 落盘融合进 chunked prefill，避免转换阶段同时保留完整 GPU KV，降低峰值并缩短 setup。
- 补 shared-mean、shared-max、独立检索的完整 GQA 候选消融，并扩大未见主题数量。
- 冻结方法后补 LongBench、RULER、Long ICL 和多主题 PPL，不再使用目标测试集调阈值。

# Section 145: b16 多块假设的 M100 复验

日期：2026-07-11

## 背景

用户提出一个合理假设：`block_size=16` 不一定“太碎”，因为 token 本来也是逐个处理的；如果每个 block 更小，就可以在同样或略高预算下选择更多 evidence block，理论上可能提升召回。

这轮实验不再只做孤立 ablation，而是把 b16 接到当前最强的 v286 memory-action planner 上，验证它能否成为实际可用的安全动作。

当前主线基线：

| Method | Samples | Score | KV keep | Online |
|---|---:|---:|---:|---:|
| v286 mined fallback router | 1600 | 0.4378 | 28.62% | 0.5676s |

## 实验设计

只替换 6 个真正依赖 evidence block 检索的 LongBench QA 任务：

- `narrativeqa`
- `qasper`
- `multifieldqa_en`
- `hotpotqa`
- `2wikimqa`
- `musique`

其它任务沿用 v286 的当前最优动作，例如 `gov_report` direct512、`qmsum` model96、`triviaqa` short4、code/retrieval 的现有策略。

三组 b16 变体：

| Run | 配置 | 目的 |
|---|---|---|
| v288 | `riskkv_task_policy_v288_v286_b16_samebudget_20260711.json` | 同预算下把 QA 任务改成 16-token block，验证“同 token 预算但更多细块”是否有效。 |
| v289 | `riskkv_task_policy_v289_v286_b16_highrecall_20260711.json` | 提高 b16 sparse budget，验证“多选更多 16-token block”的质量上界。 |
| v290 | `riskkv_task_policy_v290_v286_b16_highrecall_anchor_20260711.json` | b16 只负责定位，命中后保留 64/96/128-token 连续窗口，验证细粒度 locator + span repack 是否有效。 |

所有变体都保留 v286 的 risk/min-safe fallback 逻辑。

## 当前结论

这轮 M100 复验基本否定了“只要 b16 多选一些 block 就能整体变好”的假设。

关键不是 16-token block 本身不能用，而是当前 selector 的排序目标在细粒度下更容易选到局部相关但语义不完整的碎片。对 LongBench QA，很多任务需要的是 evidence span 或多段证据链，而不是若干孤立 token block。

可保留的正信号：

- `hotpotqa` 上 v290 达到 0.5335，高于 v286 的 0.5260。更准确地说，v286 本来已经对 hotpot 使用 b16+anchor；这次的增益来自更高 sparse budget，因此可以做成 v291 的 task-specific min-safe action。
- `multifieldqa_en` 在 v286/v288 完全一致，说明 b16 在部分直接定位任务里并非天然有害。

不建议：

- 不建议把 b16 多块作为全局主线。
- 不建议继续单纯增加 b16 budget；v289 已完成任务显示 KV 增加但质量没有稳定上升。

下一步更合理的方向：

1. 把 b16 从“最终保留单位”降级成“候选定位器”。
2. 对 hotpot/实体跳转任务保留 b16+window，并把安全预算从 2048 提高到 3072，形成 v291。
3. 对 narrative/qasper/2wiki/musique 保持 v286 的 safer action，或探索 learned span composer，而不是继续加 b16 block 数量。
4. 训练一个 action router，输入 task family、score gap、coverage、是否多跳实体问题，输出使用 `b16_locator_window`、`b128_span`、`fallback_full` 还是 `direct/short_decode`。
